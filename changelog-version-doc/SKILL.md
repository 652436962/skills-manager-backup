# CHANGELOG 版本文档规范

## 使用方式

直接描述你的 CHANGELOG 维护需求，系统会自动按需调用本 skill 的规范与脚本处理。

| 需求示例 | 自动处理 |
| -------- | -------- |
| "帮我新建一个 CHANGELOG 文件" | 复制 `assets/CHANGELOG-template.md` 起步，填写首个版本 |
| "给 V1.4.0 写一版发版说明" | 加索引行 + 显式锚点 + `###` 小节，列出修改文件 |
| "代码提交完了，把 git 号补进 CHANGELOG" | 回填索引行短号，再单独提交文档（禁止 amend） |
| "版本索引/锚点跳转乱了" | 先用 `scripts/sync_changelog_index.py --dry-run` 预览，再 `--backup` 重建 |
| "检查 CHANGELOG 格式对不对" | 运行自检命令，逐版本核对 anchor=1、section=1 |
| "规划一个新版本 V2.0.0" | 标"规划中（未实现）"，列待确认事项，索引不写 hash |

## 1. 文档骨架（必须保持）

```markdown
# CHANGELOG

## 版本索引

| 版本 | 日期/说明 |
| ---- | --------- |
| [V1.3.7](#v1.3.7) | 规划中（未实现） |
| [V1.3.6](#v1.3.6) | 2026-11-17 (1b77a14) |
| [V1.3.5](#v1.3.5) | 2026-11-17 (6055069) |

<a id="v1.3.7"></a>
## [V1.3.7] - 规划中（未实现）

> 本版本内容为设计规划，代码尚未实现。

### 规划：xxx

**命令格式**

```
#ZIGBEE,<类型>,<编号>,STATUS
```

### 待确认事项

1. ...

<a id="v1.3.6"></a>
## [V1.3.6] - 2026-11-17

### 优化：xxx

**问题**：...
**改造**：...

- 要点 1
- 要点 2

**修改文件：** `A.cpp`, `B.h`, `docs/CHANGELOG.md`

<a id="v1.3.5"></a>
## [V1.3.5] - 2026-11-17

### 缺陷修复：xxx
...
```

## 2. 硬规则

1. **索引放在文件最上方**，紧跟 `# CHANGELOG`，表格固定两列：`版本 | 日期/说明`。
2. **索引行必须是链接**：`| [V1.3.6](#v1.3.6) | 2026-11-17 (1b77a14) |`，目标锚点用版本号小写（点保留）。
3. **每个版本小节前必须有显式锚点** `<a id="v1.3.6"></a>`，一个版本一个锚点，锚点与小节数量必须相等。
4. **索引按版本号倒序**；正文小节也按新版本在前排列。
5. **git 短号只写在索引的"日期/说明"列**，小节标题保持 `## [V1.3.6] - 2026-11-17`（本项目约定，标题不带 hash）。
6. **规划中的版本**：标题写成 `## [V...] - 规划中（未实现）`，紧跟 `> ...尚未实现...` 引用说明，索引里无 git 号。
7. **每个版本正文以三级标题开头**：`### 功能新增：...` / `### 缺陷修复：...` / `### 优化：...`。推荐字段（见 `assets/CHANGELOG-template.md`）：缺陷修复用"现象 / 根因 / 修改文件"，优化用"问题 / 改造 / 要点列表"，功能新增用"命令格式 / 应答 / 验证"。
8. **代码/报文用围栏代码块**，保留原始大小写、`!`、`%`、十六进制前缀，不要"顺手美化"。
9. **结尾写修改文件**：`**修改文件：** \`文件A\`, \`文件B\``（仅文档变更时可省略）。
10. 日期统一 `YYYY-MM-DD`，中文标点，版本号 `Vx.y.z`。

## 3. 发版流程（git 号怎么进文档）

git 号无法写进它自己的提交，必须两步：

1. 改代码 + 写 CHANGELOG（该版本小节先不写 hash）
2. 提交代码，取短号：`git log --oneline -1`
3. 把短号补到**索引行**：`| [V1.3.6](#v1.3.6) | 2026-11-17 (1b77a14) |`
4. **单独提交文档**：`docs: CHANGELOG V1.3.6 补 git 号`
   - 不要用 `git commit --amend`：amend 会改掉 hash，文档里写的就失效了
5. 同步代码里的版本常量（如 `SOFTWARE_VERSION_STRING`）

## 4. 新增一个版本（清单）

- [ ] 索引表格增加一行，链接指向新锚点
- [ ] 正文最上方（或对应位置）加 `<a id="vx.y.z"></a>` + `## [Vx.y.z] - YYYY-MM-DD`
- [ ] 写 `###` 小节：背景/方案/命令/验证/修改文件
- [ ] 规划版本标注"规划中（未实现）"并列出待确认事项
- [ ] 提交代码 → 回填索引 git 号 → 提交文档
- [ ] 运行自检（见下）

## 5. 自检命令

```bash
# 锚点数 == 版本小节数（每个版本各 1 个）
grep -c '<a id="v' docs/CHANGELOG.md
grep -c '^## \[V' docs/CHANGELOG.md

# 逐版本核对：版本号从正文动态提取，不写死；每行应 anchor=1 section=1
grep '^## \[V' docs/CHANGELOG.md \
  | sed -E 's/^## \[(V[0-9.]+)\].*/\1/' \
  | sort -uV \
  | while read -r V; do
      v=$(printf '%s' "$V" | tr 'A-Z' 'a-z')
      echo "$V anchor=$(grep -c "<a id=\"$v\"></a>" docs/CHANGELOG.md) section=$(grep -c "^## \[$V\]" docs/CHANGELOG.md)"
    done
```

在 GitHub / VS Code Markdown 预览里点击索引中的版本号，应能跳到对应小节。

## 6. 索引/锚点自动重建

修改多个版本后，可用本 skill 附带脚本重建索引与锚点（保留已有索引行的说明文字和 git 号）：

```bash
# 先预览，确认无误再落盘（推荐）
python3 scripts/sync_changelog_index.py docs/CHANGELOG.md --dry-run

# 正式重建，写前自动备份为 docs/CHANGELOG.md.bak
python3 scripts/sync_changelog_index.py docs/CHANGELOG.md --backup

# 不加参数则直接写入
python3 scripts/sync_changelog_index.py docs/CHANGELOG.md
```

脚本行为：

- 解析已有 `## 版本索引` 表格中的"日期/说明"，保留其中的 git 号与说明文字
- 删除旧的索引区块与旧锚点，按版本号倒序重建索引（兼容 `V2.0.0-beta` 之类预发布号）
- 在每个版本小节标题前插入 `<a id="vx.y.z"></a>`
- 不改动小节正文、标题及索引后面其它二级章节
- 自动统一 CRLF/CR 换行；发现重复版本小节会告警（重复版本会导致锚点重复，须人工合并）
- 结果幂等：重复运行不会重复插入索引或锚点

## 7. 常见错误

| 错误 | 后果 | 正确做法 |
| ---- | ---- | -------- |
| 索引用小节自动锚点（如 `#v136---2026-11-17`） | 标题一改链接就失效 | 用显式 `<a id="v1.3.6"></a>` |
| 重复粘贴版本标题行做索引 | 产生重复锚点，跳转错位 | 索引用表格 + 链接，不重复标题 |
| 用 amend 提交来写 git 号 | 文档里的 hash 不存在 | 代码提交后再单独提交文档 |
| 小节标题也带 hash | 与索引重复、维护两处 | hash 只放索引 |
| 规划版本写 hash | 无对应提交 | 标"规划中（未实现）" |
